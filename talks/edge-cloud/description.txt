Title: Rebuilding a Search Index While the Database Keeps Changing

Your search index is disposable only if you can replace it correctly. While a replacement loads, a customer record changes twice and another is deleted. A successful bulk load says little about whether searches will return the right state after cutover.

This design walkthrough uses PostgreSQL, Debezium, Kafka on Strimzi and Elasticsearch to follow those records into a separate replacement index. We define stable document identity, repeatable updates, delete handling and a per-partition progress checkpoint. Each decision serves the same question: what evidence makes it reasonable to switch the read alias while source writes continue?

The recovery plan branches on retained history. If the stream contains the required baseline and changes, replay can reconstruct the view; otherwise, a new snapshot must be coordinated with subsequent changes. We check known insert/update/delete fixtures at a declared progress checkpoint, then define acceptable remaining lag and how new writes continue after alias cutover. The result is a rebuild runbook with an explicit freshness target, rather than an unsupported claim of instantaneous equality with the database.

Attendees will leave with:
- A recovery sequence for rebuilding a derived index while writes continue
- The roles of stable keys, ordering, deletes and event retention
- Checks for validating catch-up and controlling the switch to a replacement index
