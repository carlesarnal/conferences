SOURCE-TO-QUERY PROGRESS LEDGER
==============================
Preparation artifact based on the existing locally verified pipeline. Fill the
identifiers during rehearsal; blank fields are not missing production telemetry
claims. Do not combine offsets from unrelated partitions as one global order.

Question                         Evidence to capture
-------------------------------  -----------------------------------------------
Was the source change committed?  Table, key, operation and source transaction/LSN
Was a CDC event emitted?          Matching key/op and Kafka topic/partition/offset
Did the sink consume it?          Relevant task/partition progress and errors
Did a table commit include it?    Iceberg snapshot ID, commit time and added data
Can the query engine see it?      Query result for that key and snapshot context
Is this current row state?        Ordering/delete rule applied to the changelog

RECORDED FAILURE
Sink RUNNING did not imply commits. Control-consumer logs showed UNKNOWN_MEMBER_ID
and commits to zero tables; changing its group protocol restored commits in the
recorded setup. That is observed recovery, not an isolated root-cause proof.

RECORDED FRESHNESS
33 and 42 seconds from insert to query visibility in two local runs, including
query/polling overhead, with a 10-second configured commit interval. No per-stage
latency attribution, production SLO or throughput claim follows from those runs.

ON-STAGE WALKTHROUGH
Trace one key rather than reading every component's logs. When evidence stops at
a boundary, inspect the next stage before declaring the pipeline healthy. Show
the append-only update and its current-state query as different outputs.
