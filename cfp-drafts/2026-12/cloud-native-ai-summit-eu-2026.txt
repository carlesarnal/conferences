SUBMISSION 1: Agent Governance (flagship — Architecture & Agents)
================================================================

Session Title:
Agent Sprawl Is the New Microservice Sprawl: Discovery and Governance for Multi-Agent AI

Description:
Five teams. Twenty agents. Three frameworks. No one knows which agents talk to which — or what happens when one team's "minor update" silently breaks four downstream consumers. If this sounds familiar, it should: it's the same discovery and compatibility crisis that hit APIs a decade ago. The difference is that agents evolve faster, fail more silently, and have no contract layer by default.

I'll demonstrate publishing, discovering, and versioning A2A Agent Cards with Apicurio Registry, then show how communication schemas can be checked independently. We'll distinguish metadata discovery from runtime negotiation and structural compatibility from behavioral correctness. Integration tests are still needed when an agent's behavior changes without changing its advertised interface.

Attendees will walk away with:
- A governance architecture for agent discovery, versioning, and deprecation using A2A Agent Cards
- Concrete patterns for enforcing compatibility rules across independently evolving agents
- A clear comparison of where A2A, MCP, and traditional API governance overlap and diverge

SUBMISSION 2: Prompt Governance (Architecture & Agents — literal track match)
================================================================

Session Title:
Your Prompts Are Unversioned: Applying Schema Governance to LLM Templates

Description:
You version your code. You version your schemas. But your prompt templates live in environment variables, config files, or hardcoded strings — unversioned, ungoverned, and one edit away from breaking your AI application in ways that no test suite catches.

I'll demonstrate registering, versioning, and rendering prompt templates with Apicurio Registry, then discuss how a Quarkus/LangChain4j application can consume a selected version. We'll separate structural checks on template inputs from behavioral evaluation of model outputs: a compatible template can still produce worse answers. Version selection and rollback support controlled releases, while evaluation tests remain necessary to detect quality regressions.

Attendees will leave with:
- A reusable pattern for versioning prompt templates and checking their inputs
- An integration approach for Quarkus + LangChain4j applications consuming selected prompt versions
- A clear framework for deciding when prompt governance pays off and when it's overkill

SUBMISSION 3: Streaming ML Inference (Infrastructure & AI Inference Engineering)
================================================================

Session Title:
Classify It Before a Human Sees It: Streaming ML Inference on Kubernetes

Description:
A stream of posts arrives in Kafka. Spark Structured Streaming classifies them, and a Quarkus API serves the predictions. How do you operate this pipeline on Kubernetes while keeping up with changing input rates?

In this 25-minute session, I'll walk through a prepared pipeline and focus on Spark micro-batch intervals, backpressure, and observing the path from ingestion to predictions. We'll examine the trade-offs between throughput and latency, and the metrics needed to distinguish input lag from slow inference. This is a demonstration architecture, not a claim of measured sub-second production performance.

Attendees will leave with:
- A complete, deployable blueprint for streaming ML inference on Kubernetes
- Practical guidance on scaling Spark Streaming jobs and handling backpressure
- Patterns for extending the pipeline to other classification domains (fraud detection, content moderation, log analysis)

SUBMISSION 4 (optional): Data Contracts (Operations, Security & Governance)
================================================================

Session Title:
Why Your AI Pipeline Broke at 3 AM: Data Contracts for Event-Driven Machine Learning

Description:
An inference service can fail even when its model has not changed: an upstream producer changes a field type, and the consumer can no longer read its inputs. Independently evolving producers and consumers need explicit data contracts.

Using a Kafka-based AI pipeline as the architectural context, I'll demonstrate registering Avro contracts, accepting a compatible change, and rejecting an incompatible schema version in Apicurio Registry. We'll identify the serializer and deployment checks needed to enforce these contracts. A registry is not a broker-side firewall, and structural compatibility does not validate feature semantics or model quality.

Attendees will leave with:
- A concrete pattern for implementing data contracts in streaming AI architectures
- A comparison of schema evolution strategies (Avro, Protobuf, JSON Schema) and when each fits ML workloads
- A reproducible setup they can deploy to enforce schema governance across their own pipelines
