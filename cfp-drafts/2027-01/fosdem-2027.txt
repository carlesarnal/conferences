SUBMISSION 1: Lakehouse (Data / Cloud devroom)
Title: The Sink Said RUNNING: Is Your CDC-to-Iceberg Pipeline Making Progress?

Description:
A Kafka Connect task reports RUNNING while its logs report commits to zero tables. We trace one insert from PostgreSQL through Debezium and Kafka to an Iceberg snapshot queried by Trino. A recorded control-consumer investigation shows the change that restored commits and the limits of what it proves. Attendees get a compact source-to-query checklist distinguishing process health, consumption, committed data and query visibility.

SUBMISSION 2: Agent Discovery (AI / ML devroom)
Title: Agent Sprawl Is the New Microservice Sprawl: Discovery and Governance for Multi-Agent AI

Description:
A translator removes its declared translation skill. In a connected Quarkus workflow, an MCP weather tool feeds an A2A summarizer and translator through registry-discovered endpoints. We reject the changed Agent Card in Apicurio Registry, inspect the unchanged accepted registration and rerun the workflow. Application code owns the sequence; registry checks protect publication, not the remote implementation. Attendees get a responsibility map and executable publication checks, focused on one change for this shorter session.

SUBMISSION 3: Sandbox Journey (Community devroom)
Title: Preparing a CNCF Sandbox Application: A Maintainer's View from Apicurio Registry

Description:
In January 2024, I deferred Apicurio Registry's Sandbox application over branding questions and the xRegistry relationship. The renewed application passed its vote in March 2026, with contribution agreement and onboarding as separate steps. Following the public records, we examine project scope, ecosystem fit and ownership of the remaining work. Maintainers leave with a question/evidence/gap/owner worksheet grounded in one project's documented decisions rather than a formula promising admission.

SUBMISSION 4: Kafka Proxy (Cloud devroom)
Title: Validate Before Kafka: What Happens When a Proxy Enforces Your Schemas

Description:
A valid order reaches Kafka through a validation proxy; a schema-invalid order returns a precise error to its producer. What happens when both are sent in the same batch? Using Kroxylicious 0.24.0 and Apicurio Registry, this session follows the observed mixed-batch rejection and explains its implications for retries, ordering and duplicates. Attendees get a compact failure matrix and criteria for combining client validation with proxy enforcement.
