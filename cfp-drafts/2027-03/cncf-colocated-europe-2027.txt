1. AGENTICS DAY: MCP + AGENTS
================================================================
Topics listed include: Building MCP Servers & Clients; Security, Trust &
Reliability; Enterprise Integration & Governance.

Title:
A2A or MCP? Choosing an Interface for the Same Capability

Description:
You have a summarization service and two plausible interfaces: expose an MCP tool or publish an A2A agent. Both can accept text and return a summary. The useful comparison starts when the caller needs to understand task progress, cancel work, or respond to a failed invocation.

This session holds a deterministic summarization capability constant and invokes it over real HTTP through the official Python A2A and MCP SDKs. Both return the same eight-word result. A blank input becomes a failed A2A task and an MCP error result; progress appears as queryable A2A task state or MCP progress notifications. We then cancel a request and inspect what each client can actually observe.

The versioned observations distinguish A2A's canceled task record from MCP's canceled client request and subsequent usable session. Neither local implementation supplies durable restart recovery or production authentication. A decision table ties those limits to caller requirements rather than labels: an A2A endpoint need not contain a reasoning loop, and an MCP tool need not perform simple work.

Attendees will leave with:
- A decision table for exposing the same capability through A2A, MCP, or both
- Questions to ask about task lifecycle, authorization and failure handling
- A method for comparing interfaces without conflating protocol choice with implementation behavior

Benefits to the ecosystem:
A same-capability comparison helps MCP practitioners reason about integration
choices without treating tools as inherently simple or agents as inherently
intelligent. The decision table makes lifecycle and failure requirements explicit.

Differs from the KubeCon EU submission: interface selection for one capability,
rather than registry-backed discovery and card compatibility. The historical
submitted EU version also mentioned deprecation; the current demo does not.

CNCF context: agent integration. Demonstrated interfaces: MCP, A2A. The paired
fixture does not require a registry; registry integration is a separate example.
Case study: No.

Preparation (not form text): the separate a2a-mcp-comparison repository now runs
the same fixture over both SDKs. Use its observed behavior table, not the Paris
workflow's different capabilities, as evidence of the comparison.

2. KEYCLOAKCON
================================================================
Topics listed include: Securing Applications and Cloud Native Infrastructure
with Keycloak; Keycloak Security Best Practices.

Title:
One Keycloak Realm, Separate Trust Boundaries: Securing Kafka and Its Schema Registry

Description:
A service can have permission to publish Kafka records without having permission to change their schemas. Another can present a valid token and still be denied a topic. How do you distinguish an identity problem from an authorization decision without broadening permissions until the request works?

We exercise Keycloak, a Kafka broker using Strimzi's OAuth libraries and Apicurio Registry in a reproducible local integration lab. An invalid token returns 401; a read-only identity can fetch a schema but receives 403 when publishing a version, with accepted content unchanged. Kafka accepts an authorized producer and rejects another authenticated identity with TopicAuthorizationException; broker reads verify which record actually arrived.

The configuration walkthrough connects issuer and audience checks to principal mapping, Kafka ACLs and registry authorization. The lab exposed an outdated auth setting that left Registry authentication disabled, showing why negative controls matter. We map these findings to Kubernetes deployment responsibilities while labeling the local plaintext/admin listener as lab-only. The takeaway is a tested diagnostic method, not a production security template.

Attendees will leave with:
- A map of authentication and authorization boundaries across Kafka and its registry
- A troubleshooting table for token failures versus permission failures
- Least-privilege checks for producing, consuming and changing schemas

Benefits to the ecosystem:
Keycloak is frequently deployed in front of Kafka and schema registries, but
the boundaries between authentication and each component's authorization are
rarely shown together. This gives Keycloak users a reusable map of those
boundaries and practical checks for them.

CNCF projects: Keycloak (incubating), Strimzi (incubating), Apicurio Registry (sandbox).
Case study: No.

Before submitting: the local Compose lab now verifies OAuth and ACL denials.
It is deliberately plaintext and not a Kubernetes/TLS production template.
Use the current repository's results and label that boundary clearly.

3. CLOUD NATIVE AI + INFERENCE DAY
================================================================
Topics listed include: LLMs & Generative AI; End-to-End AI/ML in Production.

Title:
Beyond Git: Releasing and Rolling Back Runtime Prompt Templates

Description:
The prompt was reverted in Git. A running service is still using the newer template. When prompts are released independently of applications, source history does not answer the operational question: which version produced this response, and when will a rollback reach its consumers?

This session runs a release lab against Apicurio Registry and Ollama. Versioned JSON prompt artifacts carry source labels; a Python consumer explicitly selects and caches them. Application checks reject a changed required-variable contract without replacing the accepted cache. A three-question evaluation then tests instruction-only changes against predeclared format criteria, recording prompt hashes, model digest, outputs and results. In the recorded run, all candidates failed those criteria and promotion was blocked.

We separately exercise selecting an earlier artifact after a version change: the cached consumer keeps its current template until reload. The returned artifact version makes that distinction observable. The small evaluation checks format, not general answer quality; structural checks belong to the application rather than a claimed built-in prompt rule. We finish with a release checklist and when bundling prompts with application code is sufficient.

Attendees will leave with:
- A prompt-release workflow linking source revision, artifact version and consumer selection
- Separate checks for template compatibility and model-output quality
- A rollback plan that accounts for running consumers and caches

Benefits to the ecosystem:
The workflow separates authoring and review in Git from runtime distribution,
and template compatibility from output evaluation. It helps teams design
controlled prompt releases without assuming schemas guarantee answer quality.

CNCF projects: Apicurio Registry (sandbox).

Preparation (not form text): the Python release lab now exercises real Registry
selection, caching and rollback. The recorded Ollama run rejected every candidate
under the fixed format criteria; demonstrate the gate without promising quality.
