1. AGENTICS DAY: MCP + AGENTS
================================================================
Topics listed include: Building MCP Servers & Clients; Security, Trust &
Reliability; Enterprise Integration & Governance.

Title:
One Registry for MCP Tools and A2A Agents: Versioned Discovery Without a Central Gatekeeper

Description:
MCP servers describe tools; A2A Agent Cards describe agents. In most
organizations both end up scattered across repositories, wikis, and
environment variables, so nobody can answer a basic question: which versions
of which tools and agents are running, and who depends on them?

This session shows how to publish MCP server metadata and A2A Agent Cards as
versioned artifacts in Apicurio Registry, a CNCF sandbox project, so that
clients discover them the same way services discover API and schema
definitions. We'll register an agent card, publish a new version, and look at
what the registry can check — structure and declared capabilities — and what it
cannot: whether a new version still behaves the same way. We'll finish with the
integration tests and deprecation steps needed alongside the registry.

Benefits to the ecosystem:
MCP and A2A adoption is growing faster than the practices for managing them.
This talk gives MCP practitioners a concrete, open-source pattern for
versioned discovery that reuses registry techniques the cloud native community
already runs in production, and is explicit about its limits.

Differs from the KubeCon EU submission: this version is MCP-first (tool and
server metadata), 25 minutes, and focused on the registry mechanics rather than
multi-team governance.

CNCF projects: Apicurio Registry (sandbox). Other: MCP, A2A.
Case study: No.

Before submitting: the agent demo under talks/governing-agent-swarm/ has NOT
been verified end to end. Run it (and add MCP server metadata) before committing

2. KEYCLOAKCON
================================================================
Topics listed include: Securing Applications and Cloud Native Infrastructure
with Keycloak; Keycloak Security Best Practices.

Title:
One Keycloak Realm, Separate Trust Boundaries: Securing Kafka and Its Schema Registry

Description:
A producer can authenticate to Kafka and still have excessive permissions in
the schema registry. A consumer can hold a valid token and still be denied its
topic. Using one Keycloak realm for a whole data platform simplifies
credentials, but it does not make authorization consistent on its own.

This session follows a producer and a consumer through a Kafka platform built
with Keycloak, Strimzi, and Apicurio Registry. We'll separate token issuance
and validation, Kafka principal mapping and ACLs, and registry permissions,
then trace one authorized request and one denial. We'll close with token
expiry, signing-key rotation, and least-privilege access to schemas.

Benefits to the ecosystem:
Keycloak is frequently deployed in front of Kafka and schema registries, but
the boundaries between authentication and each component's authorization are
rarely shown together. This gives Keycloak users a reusable map of those
boundaries and practical checks for them.

CNCF projects: Keycloak (incubating), Strimzi (incubating), Apicurio Registry (sandbox).
Case study: No.

Before submitting: talks/security/README.md is incomplete (no working ACL
denial, HTTP on some paths). Same gaps as the NDC Security package; fix once
