SUBMISSION 1: Data Contracts for AI (Conference track)
-------------------------------------------------------

Title:
Your Model Didn't Change, Your Input Did: Data Contracts for Streaming AI Pipelines

Session Type:
Conference (45 minutes)

Abstract:
A feature changes from 30 seconds to 30,000 milliseconds while its Avro type stays long. Deserialization succeeds, but a consumer expecting seconds receives a value a thousand times larger.

We develop two checks around that feature: an incompatible revision exercises Apicurio Registry's reader/writer compatibility policy, and a normalization invariant requires both representations to yield the same model input. Java serializers and CI provide concrete enforcement points. The longer format allows a closer look at the fixture and deployment checks while keeping model-quality claims separate from input correctness.

Audience Level:
Intermediate

Tags:
Java, Kafka, AI/ML, Architecture, Quarkus


SUBMISSION 2: Real-Time Lakehouse (Tools in Action track)
----------------------------------------------------------

Title:
The Sink Said RUNNING: Is Your CDC-to-Iceberg Pipeline Making Progress?

Session Type:
Tools in Action (30 minutes)

Abstract:
The sink reports RUNNING while its logs report commits to zero tables. We trace one insert through PostgreSQL, Debezium, Kafka, Apicurio Registry and Iceberg to a Trino result. A recorded control-consumer investigation shows a change that restored commits and the limits of that diagnosis. Attendees get a checklist connecting event, offset, snapshot and query visibility, including why a commit setting is not a freshness guarantee and a changelog is not automatically current state.

Audience Level:
Intermediate

Tags:
Java, Kafka, Apache Iceberg, Kubernetes, Tools


SUBMISSION 3: Kafka Proxy (Conference track)
---------------------------------------------

Title:
Validate Before Kafka: What Happens When a Proxy Enforces Your Schemas

Session Type:
Conference (45 minutes)

Abstract:
A valid order is rejected with the same exception type as malformed data because its schema registry is unavailable. Should the producer retry or repair it? Drawing on my Avro/Protobuf validation contribution, this session examines the Java-based Kroxylicious filter through a JSON Schema demo with Apicurio Registry.

We'll trace a valid order and a rejected record, then examine observed behavior on Kroxylicious 0.24.0: mixed-batch rejection, direct broker access bypassing validation, and a registry outage rejecting valid data. A failure matrix connects producer result, broker outcome and recovery choice, with attention to ordering and duplicate handling.

Audience Level:
Intermediate

Tags:
Java, Kafka, Kroxylicious, Architecture


Speaker Bio:
Carles Arnal is a Principal Software Engineer at IBM, a core maintainer of Apicurio Registry and a Quarkus committer. He is an associate professor at BarcelonaTech (UPC). His work focuses on event-driven applications, data contracts and agent integration, with hands-on examples using Kafka, Strimzi, Debezium and Iceberg.
