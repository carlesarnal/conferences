SUBMISSION 1 — KAFKA PROXY (base demo verified September 28, 2026)
================================================================

Title:
Validate Before Kafka: What Happens When a Proxy Enforces Your Schemas

Format: 45-minute session (about 32 minutes of content + Q&A)
Level: Intermediate
Suggested tags: Java, Kafka, Architecture, Data Quality

Description:
A valid order is rejected. Its producer sees the same exception type as for
malformed data, but the registry is unavailable. Should it retry or repair the
record? Proxy validation changes the producer's failure contract.

Drawing on my Avro/Protobuf validation contribution to Kroxylicious, we use a
JSON Schema example with Apicurio Registry to trace producer errors and broker
contents. The Java filter walkthrough explains where those decisions occur.

The operational trade-offs are the focus. In the tested Kroxylicious 0.24.0
setup, an invalid record rejects its mixed batch, direct broker access bypasses
validation, and a registry outage rejects valid data with the same exception
type used for bad input. We'll examine the filter code and build a failure
matrix connecting producer result, broker outcome and recovery choice.
Selective replay requires care with ordering and duplicate handling.

Attendees will leave with:
- A failure matrix for schema errors, batch rejection, bypass and registry outages
- A method for separating data failures from infrastructure failures before retrying
- Criteria for combining client validation and proxy enforcement

Message to the program committee:
I contributed the Avro and Protobuf schema validation support to Kroxylicious's
Record Validation filter (kroxylicious/kroxylicious#3498, released in 0.21.0),
and I'm a core maintainer of Apicurio Registry, the registry the filter uses.
The demo runs on released Kroxylicious 0.24.0 and shows each behavior above
live: precise rejection errors, whole-batch rejection, a bypass through the
broker, and fail-closed behavior during a registry outage. The filter is a
Preview feature upstream, and I'll say so.

Proposed timing (45 minutes total):
  0-5:   A valid order rejected: data error or registry outage?
  5-11:  Kroxylicious architecture and where the filter sits
  11-19: Demo: valid order, three rejections with producer-side errors
  19-25: Demo: mixed batch, direct-to-broker bypass, registry outage
  25-31: Java filter walkthrough and failure matrix
  31-34: Recovery choices, ordering and duplicates
  34-45: Q&A

Additional resources:
- Kroxylicious PR: https://github.com/kroxylicious/kroxylicious/pull/3498
- Kroxylicious: https://github.com/kroxylicious/kroxylicious
- Demo: push talks/kafka-proxy-schema-validation/ to a public repository and
  link it here (not yet public).

SUBMISSION 2 — LAKEHOUSE (base demo verified September 28, 2026)
================================================================

Title:
The Sink Said RUNNING: Is Your CDC-to-Iceberg Pipeline Making Progress?

Format: 45-minute session (about 32 minutes of content + Q&A)
Level: Intermediate
Suggested tags: Java, Kafka, Data Engineering, Apache Iceberg

Description:
The sink reports RUNNING while its logs report commits to zero tables. That
observed failure starts an investigation into the difference between a healthy
process and a database change becoming queryable by an analyst.

We'll trace one insert through a running PostgreSQL, Debezium, Kafka on
Strimzi, Apicurio Registry and Apache Iceberg Kafka Connect pipeline to a Trino
query result. A recorded control-consumer investigation shows the configuration
change that restored commits, separating observed recovery from an unproven
underlying root cause.

Two local runs took 33 and 42 seconds despite a configured 10-second commit
interval. These observations include query and polling overhead and are not
production benchmarks. We'll distinguish capture, consumption, table commits
and query visibility, then use snapshot history to verify progress. The table
is an append-only changelog, so seeing events differs from reconstructing
current row state.

Attendees will leave with:
- A progress checklist from source event to query-visible snapshot
- A method for investigating a RUNNING connector that is not committing data
- A distinction between commit intervals, measured freshness and current-state queries

Message to the program committee:
The base demo was exercised on Strimzi 1.2, Kafka 4.3, Debezium 3.6,
Apicurio Registry 3.3 and Apache Iceberg 1.11. The live segment traces a running
pipeline; the failure investigation uses captured logs. Timings are local
observations, not evidence of production performance. I maintain Apicurio
Registry; an earlier version of this topic was accepted at JavaZone 2026.

Proposed timing (45 minutes total):
  0-4:   RUNNING versus making data available
  4-10:  Architecture and progress signals
  10-19: Trace one insert to a query-visible snapshot
  19-28: Investigation: coordinator logs and no table commits
  28-34: Progress checklist, observed timings and changelog semantics
  34-45: Q&A
