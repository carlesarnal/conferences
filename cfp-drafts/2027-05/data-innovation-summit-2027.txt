SUBMISSION 1: Lakehouse
Title: The Sink Said RUNNING: Is Your CDC-to-Iceberg Pipeline Making Progress?
Suggested track: Data Engineering / Data Platforms
Level: Intermediate

Description:
The sink task reports RUNNING. Its logs report commits to zero tables. The source database keeps changing, but an analyst sees nothing new. This happened while building a PostgreSQL-to-Iceberg pipeline: process health and data progress told different stories.

We follow one insert through Debezium, Kafka on Strimzi, an Avro schema in Apicurio Registry, an Iceberg table commit and a Trino query. Each stage supplies a different piece of evidence: an emitted event, a consumed offset, a committed snapshot or a query-visible row. A recorded investigation then examines the sink's control-consumer failures and the configuration change that restored commits, separating the observed recovery from an unproven underlying root cause.

Two local runs made an insert queryable after 33 and 42 seconds with a 10-second commit interval. These measurements include polling and query overhead; they illustrate why a setting is not a freshness guarantee. We finish by querying the append-only changelog as current row state, making explicit the difference between seeing an update event and seeing its effect.

Attendees will leave with:
- A source-to-query progress ledger: event identity, consumed offset, committed snapshot and visible row
- A method for investigating a RUNNING connector that is not committing data
- A practical distinction between commit intervals, measured freshness and current-state queries

Three takeaways:
- Check progress from source event to query-visible snapshot.
- Separate connector health from successful data commits.
- Distinguish changelog visibility from current-state reconstruction.

SUBMISSION 2: Data Contracts
Title: Your Model Didn't Change, Your Input Did: Data Contracts for Streaming AI Pipelines
Suggested track: AI Governance / Data Quality
Level: Intermediate

Description:
A feature value changes from 30 seconds to 30,000 milliseconds. Its Avro type stays long. Deserialization succeeds, but an inference service that expects seconds now receives a value a thousand times larger. What should a contract check before that input reaches the model?

This session develops two complementary checks around one feature. First, an incompatible schema revision tests the writer/reader compatibility policy in Apicurio Registry. Then a fixture supplies the same duration in seconds and milliseconds, with its unit explicitly declared. Both must normalize to 30 before inference; interpreting 30,000 as seconds must fail the check. We place these controls in schema publication, producer integration and CI, using an Avro/Kafka example on Strimzi.

The distinction is practical: backward compatibility asks whether a new reader can read old data; it does not certify every deployed reader or preserve the meaning of a number. A registry rejection protects its publication boundary, while the feature test checks the transformation used by inference. Attendees learn how to combine those controls without mistaking either for a guarantee of model quality.

Attendees will leave with:
- A workflow combining Avro compatibility checks with feature-input tests
- A clear account of where contracts are enforced and where they can be bypassed
- A test pattern for schema-compatible changes in units and feature meaning

Three takeaways:
- Combine Avro compatibility checks with feature-input tests.
- Identify enforcement points and bypass paths.
- Test units and feature meaning without claiming to guarantee model accuracy.
