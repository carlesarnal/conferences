SUBMISSION 1: Data Contracts for AI Pipelines
----------------------------------------------

Title:
Data Contracts for Event-Driven AI: How Schema Registries Prevent Pipeline Failures

Kind:
Presentation, 45 mins

Language:
English

Description:
45% of enterprise AI projects fail because of data quality issues, not model accuracy. The root cause? Producers and consumers in AI pipelines evolve independently, and without formal contracts, a silent schema change in one team's Kafka producer becomes a 3 AM page for another team's inference service.

In this session I'll show how data contracts enforced through Apicurio Registry (a CNCF sandbox project) bring the same discipline to AI data pipelines that API contracts brought to microservices. Using a live demo with Debezium CDC, Kafka on Strimzi, and a downstream ML inference service, I'll walk through how schema compatibility rules catch breaking changes at produce time, not at prediction time.

You'll see the registry reject incompatible schemas before they enter Kafka, preventing silent failures that would otherwise crash inference workloads hours later. I'll compare schema evolution strategies (Avro, Protobuf, JSON Schema) and show when each fits AI workloads.

Expected audience:
Java/Kotlin developers building event-driven systems, data engineers working with Kafka pipelines, ML engineers integrating models with streaming data. Attendees should have basic familiarity with Kafka concepts (producers, consumers, topics) and an understanding of why schema changes can break downstream systems. No AI/ML expertise required.

Suggested keywords:
Kafka, Schema Registry, Data Contracts, Machine Learning, Event-Driven Architecture

Outline (internal, not public):
1. The Data Quality Crisis in AI Pipelines (5 mins) - Why 45% of AI projects fail on data issues not model accuracy. Real example of schema drift causing inference failures.

2. Data Contracts = Schema + Compatibility Rules (8 mins) - What a data contract is vs just documentation. Why Kafka alone doesn't solve this. Role of Apicurio Registry in contract enforcement.

3. Live Demo: Enforcing Contracts in Practice (20 mins) - Deploy CDC pipeline PostgreSQL to Debezium to Kafka to ML service. Register input and output schemas with BACKWARD compatibility. Demonstrate compatible schema evolution (adding optional fields). Attempt breaking change (removing required field), registry rejects it. Show how this prevents downstream ML service crash.

4. Schema Formats for AI Workloads (7 mins) - Avro for compact binary high-throughput CDC. Protobuf for cross-language ML services and strong typing. JSON Schema for human-readable metadata and flexibility. When to use each.

5. Deploying This in Production (5 mins) - Integration with CI/CD (schema validation in pipeline). Multi-environment strategies (dev/staging/prod schemas). Monitoring and alerting on schema violations.

GitHub repos: apicurio-registry, debezium-ocp-etc-demo

Suggested category:
Cloud and infrastructure

Equipment:
WiFi and projector (standard). Live demo requires internet access for Kubernetes cluster connection.

Participation:
Attending both days

Additional information for program committee:
I'm a Principal Software Engineer at IBM and a core maintainer of Apicurio Registry (CNCF sandbox project). I've presented variations of this architecture at multiple conferences since 2023 (Current, DevConf, Data Saturday Oslo) and refined the demos based on audience feedback. All demo code is open-source and deployable.

This talk addresses a problem many Java shops face when adopting event-driven AI: schema drift breaks pipelines but teams don't realize it until production. The solution - schema registries with compatibility enforcement - is proven in traditional streaming but underused in AI contexts.

I'm comfortable with filming, live-streaming, and publication. I'm also open to presenting at local JavaBin meetups.


SUBMISSION 2: Database to Lakehouse in Real-Time
-------------------------------------------------

Title:
From Database to Lakehouse in Real-Time: CDC, Kafka, Apicurio, and Apache Iceberg

Kind:
Presentation, 45 mins

Language:
English

Description:
Batch ETL runs nightly. Your analysts query stale data. Your ML models train on yesterday's features. The streaming-first lakehouse replaces all of that with a single real-time pipeline, and you can build it entirely with open-source tools.

In this talk I'll demo a complete pipeline: Debezium captures row-level changes from PostgreSQL, streams them through Kafka with schemas enforced by Apicurio Registry (a CNCF sandbox project), and lands them in Apache Iceberg tables, queryable within seconds via Trino or Spark. I'll cover how automatic schema evolution works across the Kafka-to-Iceberg boundary, eliminating the manual DDL changes that plague traditional data lakes.

You'll see a column added to PostgreSQL automatically propagate through Debezium, get versioned in Apicurio Registry with BACKWARD compatibility, and update the Iceberg table schema, all without manual intervention. I'll also demonstrate Iceberg's time-travel queries for ML reproducibility.

Expected audience:
Java developers working with data pipelines, data engineers managing ETL/ELT processes, backend engineers evaluating lakehouse architectures. Attendees should understand basic SQL and Kafka concepts. Familiarity with Kubernetes is helpful but not required.

Suggested keywords:
Apache Iceberg, Change Data Capture, Kafka, Real-time Analytics, Lakehouse

Outline (internal, not public):
1. Why Batch ETL is Dead for Many Use Cases (5 mins) - Latency comparison hours vs seconds. Cost of stale data for analytics and ML.

2. The Streaming Lakehouse Stack (7 mins) - Debezium for CDC. Kafka as the streaming layer. Apicurio Registry for schema governance. Apache Iceberg as the lakehouse storage format. Trino/Spark as query engines.

3. Live Demo PostgreSQL to Iceberg in Real-Time (22 mins) - Deploy CDC infrastructure on Kubernetes. Insert data in PostgreSQL, query it immediately in Iceberg via Trino. Add a column in PostgreSQL with ALTER TABLE. Show automatic schema propagation Debezium to Apicurio to Iceberg. Query the new column with no manual DDL needed. Demonstrate Iceberg snapshots for time-travel queries.

4. Production Considerations (6 mins) - When CDC-to-lakehouse replaces batch ETL. Where hybrid patterns (batch plus streaming) still make sense. Schema compatibility strategies for evolving tables. Cost and performance tradeoffs (S3 storage, compute costs).

GitHub repos: debezium-ocp-etc-demo, apicurio-registry

Suggested category:
Data and analytics

Equipment:
WiFi and projector (standard). Live demo requires internet access for Kubernetes cluster connection.

Participation:
Attending both days

Additional information for program committee:
I've run CDC pipelines in production for several years and presented at conferences on event-driven architectures. This talk synthesizes lessons from those deployments with the emerging lakehouse pattern that's replacing traditional data lakes.

Apicurio Registry recently joined the CNCF sandbox, which has strengthened its position in cloud-native data governance. This makes the talk timely for Java developers evaluating modern data stacks.

SUBMISSION 3: Kafka Proxy Schema Validation
--------------------------------------------

Title:
Transparent Schema Validation at the Kafka Proxy Layer with Kroxylicious

Kind:
Presentation, 45 mins

Language:
English

Description:
Schema validation usually happens at the producer client, but what about legacy producers you can't modify, third-party integrations, or teams that skip validation? The schema-invalid messages still reach Kafka, and by then the damage is done.

In this session I'll introduce a different approach: enforcing schema validation transparently at the Kafka proxy layer using Kroxylicious. I'll demo a setup where a Kroxylicious filter intercepts produce requests, validates payloads against schemas stored in Apicurio Registry (a CNCF sandbox project), and rejects non-compliant messages before they ever reach the broker, without any changes to producer code.

You'll see invalid JSON rejected at the proxy, valid messages forwarded to Kafka, and how this complements client-side validation for a defense-in-depth approach. I'll cover performance implications, caching strategies, and when this pattern makes sense.

Expected audience:
Java/Kotlin developers working with Kafka, platform engineers managing shared Kafka infrastructure, architects evaluating data quality enforcement strategies. Attendees should understand Kafka producer/consumer basics and the role of schema registries.

Suggested keywords:
Kafka, Kroxylicious, Schema Validation, Data Quality, Infrastructure

Outline (internal, not public):
1. The Schema Validation Problem (5 mins) - Client-side validation works unless producers skip it. Legacy systems, third-party integrations, human error. Why catching bad data at the broker is too late.

2. Kroxylicious: A Kafka Proxy (7 mins) - What Kroxylicious is (protocol-aware Kafka proxy). How filters intercept and transform produce requests. Integration with Apicurio Registry for schema lookup.

3. Live Demo: Proxy-Layer Validation (20 mins) - Deploy Kafka plus Apicurio Registry plus Kroxylicious. Register a JSON Schema with validation rules. Send valid message through proxy, it reaches Kafka. Send invalid message (missing required field), proxy rejects it. Show error returned to producer. Verify only valid messages in Kafka.

4. When to Use This Pattern (8 mins) - Complement vs replace client-side validation. Legacy producer support. Multi-tenant Kafka clusters with untrusted producers. Performance considerations (latency, caching).

5. Production Deployment (5 mins) - Proxy deployment strategies (sidecar, gateway, per-broker). Network policies to enforce proxy usage. Monitoring and observability.

GitHub repo: kroxylicious-schema-validation

Suggested category:
Cloud and infrastructure

Equipment:
WiFi and projector (standard). Live demo requires internet access for Kubernetes cluster connection.

Participation:
Attending both days

Additional information for program committee:
Kroxylicious is an emerging project in the Kafka ecosystem that addresses a gap: enforcing policies on producers you don't control. This talk shows a practical application (schema validation) that many Java shops need but don't realize is solvable with infrastructure-layer enforcement.

I maintain Apicurio Registry and have integrated it with Kroxylicious for this exact use case. The demo is production-ready and addresses real feedback from teams running multi-tenant Kafka.

I'm comfortable with filming, live-streaming, and publication. I'm also open to presenting at local JavaBin meetups.


SUBMISSION 4: Edge to Cloud CDC Pipeline
-----------------------------------------

Title:
From Edge to Cloud: Building Real-Time Data Pipelines with Debezium, Kafka, and Apicurio on Kubernetes

Kind:
Presentation, 45 mins

Language:
English

Description:
A row changes in a PostgreSQL database at the edge. Milliseconds later, an Elasticsearch index in the cloud reflects that change, no batch jobs, no polling, no glue code. This talk shows you exactly how to build that pipeline using only open-source components on Kubernetes.

In a live demo I'll walk through each stage: capturing database changes with Debezium, enforcing schemas through Apicurio Registry (a CNCF sandbox project), streaming compact Avro-serialized events through Kafka on Strimzi, and processing them with Kafka Streams and Quarkus to keep an Elasticsearch index in sync with sub-second latency.

I've presented this architecture at multiple conferences since 2023 (Current, DevConf, Data Saturday Oslo). This version incorporates lessons learned and shows how the stack evolved after Apicurio joined the CNCF.

Expected audience:
Java/Kotlin developers building microservices or data pipelines, architects evaluating event-driven architectures, backend engineers needing to sync data across systems. Familiarity with Kafka concepts (producers, consumers, topics) is helpful but not required.

Suggested keywords:
Kafka, Change Data Capture, Kubernetes, Event-Driven Architecture, Microservices

Outline (internal, not public):
1. The Problem: Data Synchronization (4 mins) - Polling is wasteful, batch jobs are slow. Why CDC plus event streaming is the modern answer.

2. The Stack (6 mins) - Debezium for database change capture. Kafka on Strimzi as event backbone. Apicurio Registry (CNCF sandbox) for schema governance. Kafka Streams/Quarkus for stream processing. Elasticsearch as search index.

3. Live Demo: Edge to Cloud Pipeline (25 mins) - Deploy full stack on Kubernetes. Start Debezium connector for PostgreSQL. Insert/update/delete rows, see CDC events in Kafka. Schema evolution: add column, show Avro schema versioning. Stream processing with Quarkus. Query Elasticsearch, data in sync with sub-second latency.

4. Production Lessons (7 mins) - Schema compatibility pitfalls we hit. When CDC outperforms ETL, where tradeoffs lie. Handling backfills and schema migrations.

5. What Changed After CNCF (3 mins) - Apicurio Registry's CNCF sandbox acceptance. Improved Kubernetes-native deployment. Community growth and governance.

GitHub repos: debezium-ocp-etc-demo, apicurio-registry

Suggested category:
Cloud and infrastructure

Equipment:
WiFi and projector (standard). Live demo requires internet access for Kubernetes cluster connection.

Participation:
Attending both days

Additional information for program committee:
This is my most-presented talk, refined over multiple conferences since 2023. The architecture is battle-tested, the demo is reproducible, and attendees consistently ask for the GitHub repo afterward.

What makes this iteration unique: Apicurio Registry's CNCF sandbox acceptance in late 2023 validated the pattern and brought Kubernetes-native improvements that strengthen the demo.
