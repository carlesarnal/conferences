SUBMISSION 1: Data Contracts for AI (Java + AI angle)
================================================================

Session Title:
Why Your AI Pipeline Broke at 3 AM: Data Contracts for Event-Driven Machine Learning

Description:
An inference service can fail even when its model has not changed: an upstream producer changes a field type, and the consumer can no longer read its inputs. Producers and consumers evolve independently, so their data contracts need explicit compatibility rules.

Using a Kafka-based AI pipeline as the architectural context, I'll demonstrate registering Avro contracts in Apicurio Registry, accepting a compatible change, and rejecting an incompatible schema version. We'll examine where Java serializers and deployment checks must enforce these contracts, and why registry rules alone cannot stop producers that bypass them. Structural compatibility is only one layer: feature semantics and model quality still require application-level tests.

Attendees will leave with:
- A concrete pattern for implementing data contracts in streaming AI architectures
- A comparison of schema evolution strategies (Avro, Protobuf, JSON Schema) and when each fits ML workloads
- A reproducible setup they can deploy to enforce schema governance across their own pipelines

SUBMISSION 2: Edge to Cloud
================================================================

Session Title:
From Database Changes to Cloud Search: CDC Pipelines on Kubernetes

Description:
A row changes in PostgreSQL. How does that change reach a search index without a nightly batch job? This talk follows a change-data-capture pipeline built with open-source components on Kubernetes.

I'll walk through capturing changes with Debezium, streaming Avro events through Kafka on Strimzi, managing schemas with Apicurio Registry, and connecting stream processing to Elasticsearch. We'll examine schema evolution, consumer lag, replay, and the trade-offs involved in keeping a derived search index consistent with its source. The focus is a demonstration architecture, not a claim of measured production latency.

Attendees will leave with:
- A reproducible, fully containerized CDC pipeline they can deploy on any Kubernetes cluster
- Practical lessons on schema evolution, compatibility enforcement, and production pitfalls
- A clear framework for when CDC outperforms traditional ETL and where the tradeoffs lie

SUBMISSION 3: Kafka Proxy Schema Validation (deep JVM)
================================================================

Session Title:
Bad Messages Should Never Reach the Broker: Schema Validation at the Kafka Proxy Layer

Description:
Schema validation usually happens at the producer client — but what about legacy producers you can't modify, third-party integrations, or teams that simply skip validation? Those schema-invalid messages still reach Kafka, and by the time a consumer fails on bad data, the damage is done and the offset has moved.

In this session, I'll demo a different approach: enforcing schema validation transparently at the proxy layer using Kroxylicious, a protocol-aware Kafka proxy written in Java. A proxy filter intercepts produce requests, validates payloads against schemas stored in Apicurio Registry (CNCF sandbox), and rejects non-compliant messages before they ever reach the broker — with zero changes to producer code. I'll show the setup end to end: the Java filter implementation, registry integration, and deployment on Kubernetes.

Attendees will leave with:
- An understanding of Kafka proxy-layer architecture and how Kroxylicious filters work
- A deployable schema validation filter configuration for their own clusters
- A clear decision framework for when proxy-layer validation complements or replaces client-side checks

SUBMISSION 4: Real-Time Lakehouse (accepted at JavaZone)
================================================================

Session Title:
Kill the Nightly Batch: Building a Real-Time Lakehouse with CDC, Kafka, and Apache Iceberg

Description:
Batch ETL runs nightly. Your analysts query stale data. Your ML models train on yesterday's features. The streaming-first lakehouse replaces all of that with a single, real-time pipeline — and you can build it entirely with open-source tools on Kubernetes.

I'll demonstrate a CDC-to-lakehouse pipeline: Debezium captures PostgreSQL changes, Kafka carries the events, and Flink writes to Apache Iceberg for downstream queries. We'll examine a supported schema evolution, a breaking change, and the role of registry compatibility checks. The session explains how checkpointing, table commits, and consumer compatibility affect freshness and correctness; schema checks do not guarantee data quality on their own.

Attendees will leave with:
- A deployable CDC-to-Iceberg pipeline architecture using only open-source components on Kubernetes
- Practical patterns for handling schema evolution across the Kafka-to-Iceberg boundary
- A clear framework for when streaming lakehouse replaces batch ETL and where hybrid patterns still win
