SUBMISSION 1 — RECOMMENDED FIRST

Title:
One Identity Provider, Separate Trust Boundaries: Securing Kafka and Its Schema Registry

Description:
A producer can authenticate to Kafka and still have excessive permissions in
the schema registry. A consumer can possess a valid token and still be denied
access to its topic. Sharing an identity provider makes credentials easier to
manage, but it does not make authorization policies consistent automatically.

This session follows a producer and a consumer through a Kafka data platform
using Keycloak, Strimzi, and Apicurio Registry. We'll separate token issuance
and validation, Kafka principal mapping and ACLs, registry permissions, and
transport security. We'll examine how OAuth2/OIDC and TLS serve different
purposes, and where mutual TLS is a separate design choice rather than an
automatic consequence of enabling OAuth.

Through configuration examples and focused demonstrations, we'll trace an
authenticated request and an authorization failure, then discuss token expiry,
signing-key rotation, service identities, and least-privilege access to schemas.
The examples use open-source projects; the trust-boundary analysis applies
to other event-driven platforms too.

Attendees will leave with:
- A map of the authentication and authorization boundaries in a Kafka platform
- A method for diagnosing token-validation failures separately from permission failures
- Practical checks for topic access, schema access, and credential lifecycle

SUBMISSION 2 — OPTIONAL SECOND PROPOSAL

Title:
Validate Before Kafka: Schema Enforcement at the Proxy Boundary

Description:
Client-side validation depends on every producer doing the right thing.
Legacy clients, third-party integrations, and configuration mistakes can
still send records that consumers cannot parse. What changes when validation
is enforced on the path to the broker?

Using Kroxylicious and Apicurio Registry, this session explores a Kafka proxy
that checks record payloads against schemas before forwarding produce requests.
I'll demonstrate valid and invalid records, explain where the filter sits in
the Kafka protocol path, and examine how failures are returned to producers.

We'll then stress-test the architecture on paper: what happens when the
registry is unavailable, producers bypass the proxy, or an invalid record
appears inside a batch? We'll discuss schema caching, failure policies,
network controls, observability, and the cost of adding another component
to the write path.

Schema validation is one input-validation control. It does not authenticate
producers, enforce business semantics, or make schema-valid payloads safe.
The goal is a clear understanding of where proxy enforcement adds protection,
and where Kafka authorization and application-level checks remain essential.

Attendees will leave with:
- An understanding of the validation boundary between producer, proxy, and broker
- A decision framework for client-side versus proxy-side schema enforcement
- A failure-mode checklist covering bypass routes, registry outages, and retries

Suggested format: Regular talk (60 minutes)
Suggested level: Intermediate
Suggested topics: Security Tooling; Architecture; Cloud and Containers
Language: English
Audience: Kafka platform engineers, backend developers, and security engineers.
Case study, if asked: No — architecture and demonstration.

This proposal treats schema validation as a limited defense-in-depth measure,
