Title:
One Keycloak Realm, Separate Trust Boundaries: Securing Kafka and Its Schema Registry

Description:
A service can have permission to publish Kafka records without having permission to change their schemas. Another can present a valid token and still be denied a topic. How do you distinguish an identity problem from an authorization decision without broadening permissions until the request works?

We exercise Keycloak, a Kafka broker using Strimzi's OAuth libraries and Apicurio Registry in a reproducible local integration lab. An invalid token returns 401; a read-only identity can fetch a schema but receives 403 when publishing a version, with accepted content unchanged. Kafka accepts an authorized producer and rejects another authenticated identity with TopicAuthorizationException; broker reads verify which record actually arrived.

The configuration walkthrough connects issuer and audience checks to principal mapping, Kafka ACLs and registry authorization. The lab exposed an outdated auth setting that left Registry authentication disabled, showing why negative controls matter. We map these findings to Kubernetes deployment responsibilities while labeling the local plaintext/admin listener as lab-only. The takeaway is a tested diagnostic method, not a production security template.

Attendees will leave with:
- A map of authentication and authorization boundaries across Kafka and its registry
- A troubleshooting table for token failures versus permission failures
- Least-privilege checks for producing, consuming and changing schemas

SUBMISSION 2 — OPTIONAL SECOND PROPOSAL

Title:
Validate Before Kafka: What Happens When a Proxy Enforces Your Schemas

Description:
A valid order is rejected. The producer sees the same exception type it would receive for malformed data, but the schema registry is unavailable. Should it retry, repair the record, or stop? Moving schema validation into a Kafka proxy changes more than where bad data is caught: it changes the producer's failure contract.

Drawing on my contribution to Kroxylicious's Avro and Protobuf validation support, this session examines that contract through a reproducible JSON Schema example with Apicurio Registry. We follow an order from producer to broker, then compare a schema-invalid record, a mixed batch, a registry outage and a direct-to-broker bypass.

In the tested Kroxylicious 0.24.0 setup, one invalid record rejects its mixed batch, the outage rejects valid data, and bypassing the proxy stores an invalid record. These observations become a failure matrix connecting client errors to broker contents and recovery choices. We examine the ordering and duplicate-handling questions behind resending valid records, and the network and authorization controls needed to make the proxy an enforcement point.

Attendees will leave with:
- A failure matrix for schema errors, batch rejection, bypass routes and registry outages
- An error-handling decision tree using constraint details and SCHEMA_RESOLUTION_ERROR, not exception type alone
- Criteria for choosing client-side validation, proxy enforcement, or both

Suggested format: Regular talk (60 minutes)
Suggested level: Intermediate
Suggested topics: Security Tooling; Architecture; Cloud and Containers
Language: English
Audience: Kafka platform engineers, backend developers, and security engineers.
