SUBMISSION 1: AGENT DISCOVERY
----------------------------
Title: Agent Sprawl Is the New Microservice Sprawl: Discovery and Governance for Multi-Agent AI
Audience: Intermediate

Description:
A translator publishes a new Agent Card with its translation skill removed. Can callers catch that change before adopting the new contract? A shared registry can check the publication, but it cannot prove that the running translator still behaves as advertised. That boundary matters when agents and tools evolve independently.

This session follows a tested Quarkus workflow: an MCP weather tool feeds an A2A summarizer, whose output feeds an A2A translator. Apicurio Registry supplies endpoint metadata; application code owns the roles and sequence. We remove the declared translation skill and inspect the rejected publication, the unchanged accepted registration and a successful workflow rerun. An additive change demonstrates the accepted path. The weather data is fictional; the protocol calls and handoffs execute end to end.

My merged Quarkus LangChain4j fix supplies a second lesson: restarting an agent with a changed card must update its registration even when the declared agent version stays the same. We examine the regression test alongside the workflow's publication checks. Together they establish a responsibility matrix for fresh metadata, application-owned sequencing and runtime verification, including when static endpoints are simpler.

Attendees will leave with:
- Criteria for choosing registry-backed discovery over static endpoint configuration
- A runnable MCP-to-A2A workflow with tests for actual handoffs and contract publication
- A responsibility matrix for registry checks, application orchestration and deployment testing

Elevator Pitch:
A registry can reject an incompatible Agent Card, but it cannot stop someone deploying incompatible agent code. A connected MCP-to-A2A workflow makes that boundary visible: actual handoffs, a rejected skill removal, an unchanged accepted registration and a successful rerun. Java developers get executable checks and a clear division of responsibilities.

Notes:
I am a core maintainer of Apicurio Registry and a Quarkus committer. The current demo uses local models through Ollama and a connected MCP weather -> A2A summarizer -> A2A translator workflow. I would start with the services already running and show the actual handoffs, a rejected Agent Card change and a compatible addition. I authored merged publisher fix #2897 and open workflow sample #2932; links and status are in talks/EVIDENCE.txt. The typed MCP wrapper is backup material. Paris acceptance is confirmed and funded; that presentation is still upcoming.

SUBMISSION 2: LAKEHOUSE
----------------------
Title: The Sink Said RUNNING: Is Your CDC-to-Iceberg Pipeline Making Progress?
Audience: Intermediate

Description:
The sink task reports RUNNING. Its logs report commits to zero tables. The source database keeps changing, but an analyst sees nothing new. This happened while building a PostgreSQL-to-Iceberg pipeline: process health and data progress told different stories.

We follow one insert through Debezium, Kafka on Strimzi, an Avro schema in Apicurio Registry, an Iceberg table commit and a Trino query. Each stage supplies a different piece of evidence: an emitted event, a consumed offset, a committed snapshot or a query-visible row. A recorded investigation then examines the sink's control-consumer failures and the configuration change that restored commits, separating the observed recovery from an unproven underlying root cause.

Two local runs made an insert queryable after 33 and 42 seconds with a 10-second commit interval. These measurements include polling and query overhead; they illustrate why a setting is not a freshness guarantee. We finish by querying the append-only changelog as current row state, making explicit the difference between seeing an update event and seeing its effect.

Attendees will leave with:
- A source-to-query progress ledger: event identity, consumed offset, committed snapshot and visible row
- A method for investigating a RUNNING connector that is not committing data
- A practical distinction between commit intervals, measured freshness and current-state queries

Elevator Pitch:
A Kafka Connect task reported RUNNING while its Iceberg table received no commits. That failure is the starting point for this talk. Rather than touring a stack, I trace where a database change becomes visible and show how to distinguish process health from data progress. The example gives Java and data engineers a troubleshooting method they can use beyond this particular pipeline.

Notes:
The pipeline uses Debezium, Kafka Connect, Apicurio Registry, Apache Iceberg and Trino. It will be deployed before the session; the live portion follows an insert and its query visibility, with logs from the earlier failure. The measured timings are local observations, not a production benchmark. A shorter session could focus on the RUNNING/no-commits investigation and progress checklist. An earlier version of the lakehouse topic was accepted at JavaZone 2026.

SUBMISSION 3: KAFKA PROXY
------------------------
Title: Validate Before Kafka: What Happens When a Proxy Enforces Your Schemas
Audience: Intermediate

Description:
A valid order is rejected. The producer sees the same exception type it would receive for malformed data, but the schema registry is unavailable. Should it retry, repair the record, or stop? Moving schema validation into a Kafka proxy changes more than where bad data is caught: it changes the producer's failure contract.

Drawing on my contribution to Kroxylicious's Avro and Protobuf validation support, this session examines that contract through a reproducible JSON Schema example with Apicurio Registry. We follow an order from producer to broker, then compare a schema-invalid record, a mixed batch, a registry outage and a direct-to-broker bypass.

In the tested Kroxylicious 0.24.0 setup, one invalid record rejects its mixed batch, the outage rejects valid data, and bypassing the proxy stores an invalid record. These observations become a failure matrix connecting client errors to broker contents and recovery choices. We examine the ordering and duplicate-handling questions behind resending valid records, and the network and authorization controls needed to make the proxy an enforcement point.

Attendees will leave with:
- A failure matrix for schema errors, batch rejection, bypass routes and registry outages
- An error-handling decision tree using constraint details and SCHEMA_RESOLUTION_ERROR, not exception type alone
- Criteria for choosing client-side validation, proxy enforcement, or both

Elevator Pitch:
I contributed Avro and Protobuf validation to Kroxylicious. This talk goes beyond showing a filter reject bad JSON: one invalid record affects its batch, direct broker access bypasses validation, and a registry outage can reject valid data. Java developers get a live example, a look at the filter code, and practical guidance on handling the failures that adding validation creates.

Notes:
The demo uses the released Record Validation filter in Kroxylicious 0.24.0 and Apicurio Registry. The live examples use JSON Schema; my Avro and Protobuf contribution provides implementation background rather than a claim that those formats are demonstrated. I will distinguish observed behavior in this version from general deployment guidance. This can also be a shorter session focused on mixed-batch rejection and producer error handling. Contribution: https://github.com/kroxylicious/kroxylicious/pull/3498
