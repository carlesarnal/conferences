SUBMISSION 1: AGENT DISCOVERY
----------------------------
Title: Agent Sprawl Is the New Microservice Sprawl: Discovery and Governance for Multi-Agent AI
Audience: Intermediate

Description:
A translator publishes a new Agent Card with its translation skill removed. What should reject that change, and what does the rejection actually protect? This session follows a tested Quarkus workflow: an MCP weather tool feeds an A2A summarizer, whose output feeds an A2A translator.

Apicurio Registry supplies endpoint metadata; application code owns the roles and sequence. We inspect the rejected skill removal, confirm that the accepted registration is unchanged, and rerun the connected workflow. An additive change demonstrates the accepted path. My merged Agent Card republishing fix supplies the second lesson: a restarted agent must refresh changed metadata even when its declared agent version is unchanged.

Attendees get a runnable discovery pattern and a responsibility matrix for publication checks, orchestration and runtime verification. A valid card does not prove that deployed code honors it; static endpoint configuration may still be the simpler choice.

Elevator Pitch:
A registry can reject an incompatible Agent Card, but it cannot stop someone deploying incompatible agent code. A connected MCP-to-A2A workflow makes that boundary visible: actual handoffs, a rejected skill removal, an unchanged accepted registration and a successful rerun. Java developers get executable checks and a clear division of responsibilities.

Notes:
I am a core maintainer of Apicurio Registry and a Quarkus committer. The current demo uses local models through Ollama and a connected MCP weather -> A2A summarizer -> A2A translator workflow. I would start with the services already running and show the actual handoffs, a rejected Agent Card change and a compatible addition. I authored merged publisher fix #2897 and open workflow sample #2932; links and status are in talks/EVIDENCE.txt. The typed MCP wrapper is backup material. Paris acceptance is confirmed and funded; that presentation is still upcoming.

SUBMISSION 2: LAKEHOUSE
----------------------
Title: The Sink Said RUNNING: Is Your CDC-to-Iceberg Pipeline Making Progress?
Audience: Intermediate

Description:
The sink task reports RUNNING; its logs report commits to zero tables. We trace one insert through PostgreSQL, Debezium, Kafka on Strimzi, Apicurio Registry and the Iceberg Kafka Connect sink to a Trino result, asking what evidence proves progress at each boundary.

A recorded investigation examines control-consumer failures and the configuration change that restored commits, without claiming a proven underlying root cause. Two local freshness observations, 33 and 42 seconds with a 10-second commit interval, include polling/query overhead. They show why configuration is not a freshness guarantee. Snapshot and current-state queries distinguish a stored change event from its effect.

Attendees get a progress checklist and a method for investigating a connector that looks healthy but is not delivering data.

Elevator Pitch:
A Kafka Connect task reported RUNNING while its Iceberg table received no commits. That failure is the starting point for this talk. Rather than touring a stack, I trace where a database change becomes visible and show how to distinguish process health from data progress. The example gives Java and data engineers a troubleshooting method they can use beyond this particular pipeline.

Notes:
The pipeline uses Debezium, Kafka Connect, Apicurio Registry, Apache Iceberg and Trino. It will be deployed before the session; the live portion follows an insert and its query visibility, with logs from the earlier failure. The measured timings are local observations, not a production benchmark. A shorter session could focus on the RUNNING/no-commits investigation and progress checklist. An earlier version of the lakehouse topic was accepted at JavaZone 2026.

SUBMISSION 3: KAFKA PROXY
------------------------
Title: Validate Before Kafka: What Happens When a Proxy Enforces Your Schemas
Audience: Intermediate

Description:
A valid order is rejected with the same exception type as malformed data because the registry is unavailable. Should its producer retry or repair it? This session examines how proxy validation changes the producer's failure contract, using Kroxylicious and Apicurio Registry.

Drawing on my Avro/Protobuf validation contribution, the demo uses JSON Schema on Kroxylicious 0.24.0. A mixed batch, direct-to-broker bypass and registry outage expose distinct boundaries: valid records can be rejected with invalid ones, invalid records can bypass the proxy, and a dependency failure can look like a data error.

A failure matrix connects what the producer sees, what reaches Kafka, and whether to correct input, retry, or change deployment controls. Attendees learn when client-side validation and proxy enforcement complement each other, with attention to ordering and duplicate handling.

Elevator Pitch:
I contributed Avro and Protobuf validation to Kroxylicious. This talk goes beyond showing a filter reject bad JSON: one invalid record affects its batch, direct broker access bypasses validation, and a registry outage can reject valid data. Java developers get a live example, a look at the filter code, and practical guidance on handling the failures that adding validation creates.

Notes:
The demo uses the released Record Validation filter in Kroxylicious 0.24.0 and Apicurio Registry. The live examples use JSON Schema; my Avro and Protobuf contribution provides implementation background rather than a claim that those formats are demonstrated. I will distinguish observed behavior in this version from general deployment guidance. This can also be a shorter session focused on mixed-batch rejection and producer error handling. Contribution: https://github.com/kroxylicious/kroxylicious/pull/3498
